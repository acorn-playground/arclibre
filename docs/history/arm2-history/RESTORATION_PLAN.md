# Proposed kernel-only restoration milestone

## Baseline and outcome

Use Kernel **`3da129d209b2c78d19f6c28d9a8f15cd6f1c3bfc`**, HdrSrc **`c9113ab79d9ca2ccc49a9b7518911132ca9ffa1b`**, and the matching public module-header cohort. Preserve each source snapshot and express every change as a reviewable patch. This is the smallest identified restoration base, **not a claim that 3.60 is the desired operating-system behaviour**.

The milestone ends at one fully resolved, statically inspected ARM2 kernel component. The ultimate contract remains RISC OS **3.11** applications, original desktop, games and utilities. The compatibility work described below is specification and kernel-interface checking; it does not start integrating the desktop or applications.

## Work packages and estimates

Estimates assume an engineer familiar with ARM2/26-bit assembly, access to the existing working AsAsm, and lawful public documentation sufficient to resolve interface questions. They include investigation and review, not only editing. These are ranges inferred from the observed coupling, not measured implementation effort. Complete assembly has not yet exposed every defect.

Roughly 3–5 working weeks before contingency for one appropriately experienced engineer. This does not estimate a working ROM or 3.11 desktop compatibility; both remain substantially broader projects. An unavailable essential source/licence or irreconcilable ABI requirement should stop the milestone rather than consume open-ended contingency.

## Changes deliberately avoided by this baseline

The 3.60 import does not contain the later hard-reset `L1L2PTenhancements`/`AMBControl_Init` integration or the unconditional AMB include. It therefore does not require implementing an ARM600-style application memory manager on MEMC1. Do not import those subsystems merely to match a newer branch. The later IOMD `OS_ReadSysInfo 8` implementation is also absent; adding later query reasons is not a requirement of a 3.11 compatibility target.

If a later baseline were selected instead, it would require additional review of AMB allocation/mapping semantics, `PhysRamTable`, fixed 4 KiB pages, L1/L2 table operations, and every caller, plus original-hardware alternatives for the IOMD query and `ResetType` producers/consumers. Removing calls or returning success without the corresponding functionality would conceal these contracts. That larger route is not included in the estimate and is not recommended by this investigation.

The five-year source/version difference is not itself a compatibility argument. Build a traceable requirements table for 3.11 SWIs, OS_Byte/OS_Word, vectors, module entry conventions, application slots/dynamic areas, VDU modes, palette/pointer behaviour, system font, sound and keyboard/timer behaviour. Mark unchanged, changed, absent and unknown semantics. Use the existing compatibility plan for later milestones. Do not change version reporting to “3.11” merely to persuade applications that compatibility has been achieved.

## Acceptance and stop gates

1. **Input and licence gate:** all selected source/generated inputs have pinned public provenance and notices. Later interface substitutions are individually reviewed and recorded as restoration changes. No resources or code extracted from a ROM image.
2. **Assembly gate:** resolved component with no undefined/imported kernel symbols, no unexplained warnings or pass-size differences, and repeatable bytes from identical inputs. Preserve logs, include graph, tool hashes and patches.
3. **Architecture gate:** independent emitted-instruction audit and executable-range/reachability record for reset, IRQ, FIQ, SWI, abort and callback paths; verified 26-bit PSR-in-PC conventions; original MEMC/VIDC/IOC configuration and workspace mapping. Data words must not be casually classified as instructions or vice versa.
4. **Compatibility gate for this milestone:** explicit 3.11-facing kernel contract and unresolved behavioural risks. Static closure is not proof that desktop applications or games work.

Stop for an essential undocumented interface, a workspace change that cannot be justified without fabricating an ABI, a required dependency lacking a lawful public source, or an architectural requirement that would turn this into a larger redesign. Produce a reviewed result before any separate ROM/boot milestone. No implementation patches from this plan were applied during the historical investigation.
