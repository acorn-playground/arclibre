# RISC OS 3.11 compatibility test plan

25 October 2026. **Proposed tests and thresholds; zero ROM or application runs performed.** The acceptance target is existing unmodified software on **A440/1 ARM2 with 4 MiB**, then the same machine with ARM3. No successful Risc PC/StrongARM run or version string substitutes for this baseline.

## Reference and evidence rules

Use a privately supplied, lawfully licensed **3.11** ROM. Record its SHA-256, locale, module inventory and release identification, emulator commit/configuration, CMOS, RTC epoch, storage contents and each application's exact release/hash. A 3.10 run is a separately labelled historical comparator. It cannot supply an expected result when 3.11 has not been measured.

The published [PRM index](https://www.riscos.com/support/developers/prm/index.html) separates original chapters from the 3.5/3.6 supplement. Use base-era contracts to design tests, verify reason-code availability against 3.11, and retain a provenance tag for each expectation: **D** documented contract, **Q** observed 3.11 quirk, **H** direct-hardware requirement. Published documentation is research material, not a licence to reproduce its text, code examples or images wholesale. The [4corn archive](https://www.4corn.co.uk/archive/docs/) supplies the RISC OS 3 PRM volumes and a 3.10 release note; the latter is explicitly not a 3.11 behavioural oracle.

Before testing, enumerate the reference’s resident and ROM modules, including unplugged modules, and its resource/boot dependencies. Public [module-database metadata](https://www.marutan.net/db/) lists 3.11, but its product query returned HTTP 500 in this audit. **An exact shipped 3.11 module/version roster is therefore not asserted here.** Candidate source availability is mapped below; no percentage of the complete 3.11 stack can yet be responsibly given.

## Reproducible corpus

### Original public tests to author later

1. **ARM2/SWI probe:** controlled registers and guard words; `OS_Write0` of an original fixed string; unknown XSWI and non-X handler; original module logs vectors/services; explicit abort/recovery probe. Expected values are written from documentation or measured from lawful 3.11; unspecified registers are not compared as if specified.
2. **MEMC/RMA probe:** allocate/release/grow, exercise 32 KiB pages on the primary 4 MiB machine, verify preserved payload hashes, fault on protected/unmapped pages, and check memory after cleanup. Repeat on supported smaller-RAM profiles as separate tests.
3. **BASIC and CLI utility:** original tokenised BASIC source using integer/string operations, `SYS`, file save/reopen and sound; an original Absolute utility that copies a patterned file, checks metadata/EOF and loads/unloads an original module. Precise expected file bytes, error numbers and register effects are versioned with each case.
4. **Two-task WIMP fixture:** original app creates a window, writable icon, icon-bar icon and menu, handles redraw rectangles, and exchanges recorded/unrecorded messages and drag-save data with a peer. Log event fields and memory sentinels; exercise cancel, close and task restart. Recycled task handles/addresses may be normalised only where identity relationships are preserved.

These are plans; no test program or fixture was implemented in Phase 0. Public fixtures must be original or explicitly redistributable. Test expected behaviour, never ship extracted ROM instructions or resources.

For direct-hardware coverage, initially tag the last three as **suspected**, then classify actual MMIO/vector accesses from external traces. A game's reputation is not proof of its implementation. If none exercises a necessary hardware path, add a lawful qualifying title or an original hardware test rather than pretending coverage exists.

The small positive gate should retain at least **four desktop applications/utilities, two existing BASIC programs/applications, and three existing games**, with the named cases above providing candidates. Acorn bundled applications alone are not enough; include at least one independent complex desktop application. The exact positive membership remains blocked on reference qualification and lawful editions, not on internet availability.

### Negative and boundary set

- An original RISC OS 2-era game release that demonstrably fails under the private 3.11 baseline (an original Zarch release is a candidate, **not asserted here as universally incompatible**). Keep its actual failure as a boundary; a later fixed edition is a different binary.
- A documented 32-bit-only RISC OS 5 application: rejection or an informative unsupported-environment result is expected; a crash is still a robustness defect.
- A Toolbox-dependent application with extensions absent, then present under a separately licensed extension profile. Do not score the absent-extension failure as missing stock 3.11 functionality.
- Wrong filetype, truncated Absolute/module, malformed disc and insufficient-memory fixtures created by the project. Verify bounded failure and no file corruption.

## Differential harness design for MacArch

Use the pinned source in [BUILD_AND_TEST_STRATEGY](BUILD_AND_TEST_STRATEGY.md). Explicitly select A440/1, ARM2, 4096 KiB, standard monitor, fixed RTC epoch and known CMOS; ARM3 is a separate run. Disable real-time advance, schedule keyboard/mouse inputs by guest ticks, and capture register/memory/output/event results at named test checkpoints. Existing watchpoints, trace and CLI audio/screenshot capture provide useful foundations. A complete SWI entry/exit recorder and test scheduler are **proposed**, not claimed as an existing single MCP tool. [M8](SOURCE_AND_LICENSES.md#m8) [M9](SOURCE_AND_LICENSES.md#m9) [M10](SOURCE_AND_LICENSES.md#m10) [M12](SOURCE_AND_LICENSES.md#m12)

Create one clean starting state **per ROM**. MacArch rejects snapshot restoration with a different ROM hash; never restore a proprietary-ROM snapshot into a replacement. Hard discs are reattached rather than rolled back, so use a fresh disposable copy of each disc per run and hash it before/after. Freeze RTC/external input; check whether podules/network devices add nondeterminism. Repeat inputs from a reset as well as within-ROM snapshots to reveal hidden-state dependence. [M7](SOURCE_AND_LICENSES.md#m7)

Capture meaningful observables: input/output registers and flags where defined, error blocks, public API outputs, original test buffers, file bytes and metadata, WIMP messages, frame geometry/palette and audio events/samples. Keep private screenshots/traces containing proprietary material private. Replacing artwork is allowed, so compare geometry, metrics, clipping and interaction rather than requiring identical desktop pixels. Custom original test sprites can use exact pixel hashes. Define audio/timing tolerances **before** candidate evaluation from repeated baseline runs; unexplained drift is a failure, not an automatic widened tolerance.

## Scorecard and proposed acceptance thresholds

Each result record contains: test ID; D/Q/H provenance; ROM/config/application hashes; expected and observed values; boot/CLI/binary/desktop/launch/session fields; repeat count; evidence files; and failure class. Use `PASS`, `FAIL`, `NOT RUN`, `BLOCKED`, or `EXPECTED EXCLUSION`. Launch success is separate from a correct representative session.

| Tier | Gate to claim it | Current result |
|---|---|---|
| 0 Boot | Ten repeatable cold resets to the named observable checkpoint, correct target CPU/mapping, no unexplained exception | NOT RUN |
| 1 Core OS | Tier 0 plus all mandatory core probes and interactive CLI, clean failure paths and no unexplained state corruption | NOT RUN |
| 2 Loading | Tier 1 plus original utility/BASIC/module cases and representative disc/filetype/loading tests; **zero byte/metadata corruption** | NOT RUN |
| 3 Desktop | Tier 2 plus two-task WIMP fixture, Filer and font/resource cases; save/reload, messages, menus and slot switching all pass | NOT RUN |
| 4 Library | All qualified positive cases complete their scripted sessions, three clean repeats each on the claimed CPU profile; all required software categories represented; no unwaived crash, data corruption, material rendering/audio/input defect or nondeterministic failure | NOT RUN |

Ten resets and three sessions are proposed initial repeatability gates, not statistical proof of exhaustive compatibility. Require a representative timed session (for example, one complete selected game level or an edit/save/reopen task), not a fixed amount of idle emulation. Publish the exact corpus and limitations; a sample cannot establish the whole library works. For the release gate, repeat a common A3000/ARM2 subset in an independent emulator and retain the A440/1-specific cases in MacArch and eventually hardware.

Report separately: **architecture/missing OS**, **semantic mismatch**, **hardware/timing**, **ROM/RAM capacity**, **unlicensed/missing dependency**, **emulator limitation**, and **unqualified input**. Within actual runs distinguish crash/hang, missing functionality, rendering, sound, input, file corruption and nondeterminism. Do not turn licence blockage into a compatibility failure or use a SWI-count percentage as acceptance.
